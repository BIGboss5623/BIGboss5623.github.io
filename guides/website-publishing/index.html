一个源码仓库，两条静态发布链路：从故障到可验证上线

代码推送成功不代表网站已经发布；公开网页可用也不等于私有数据接口健康。这里整理一个多站点项目中实际采用的分层验收方法。

首次发布：2026 年 11 月 25 日 · 结合实际部署经验持续核验

一、把一次“上线成功”拆成四件事

阶段应该验证什么常见误判
Git 源码远端分支与本地提交 SHA 是否一致误把 git push 的返回码当成网站已更新
静态构建与 CI测试是否真正运行，构建是否成功产生产物仅在 Windows 本地通过，忽略 Linux CI 环境差异
公开网站部署HTTP 状态、关键内容、手机与桌面浏览器功能GitHub Pages 已成功却未验证 Cloudflare 主域名
私有业务后端后台健康、鉴权、数据接口及依赖服务公开首页 HTTP 200 就宣称整套服务健康

二、纯静态网站遇到 Jekyll 构建冲突

若仓库本身已有完整 HTML、CSS、JavaScript 文件，而 GitHub Pages 又自动运行 Jekyll，就可能因为输出路径与已有静态目录冲突而失败。对不需要 Jekyll 转换的纯静态站，可在仓库根目录使用空文件 .nojekyll，让 GitHub Pages 直接按静态文件发布。

这个选择不会替代 Cloudflare Pages 的部署，也不应该用来解决所有构建失败；应先查看 GitHub Actions 中失败步骤的真实日志，再实施针对性修复。

三、跨仓库依赖是 CI 中容易忽略的一层

有些网站将主导航、企业站和其他公开子站拆成独立仓库。本地开发环境中，相邻目录可能已经存在，因此链接审计通过；GitHub Actions 默认仅检出当前仓库，相邻目录缺失，就可能被判定为断链。

可在 CI 里只读检出对应的公开仓库到约定的相邻目录，再运行跨站审计。这样既不需要把无关源码复制多份，也不必禁用已经发现问题的测试。

四、让搜索引擎正确发现多域名内容

  • 让公开页面拥有具体、与正文一致的标题与摘要，而不是所有页面重复“首页”。
  • 通过规范地址 rel="canonical" 指明相同内容在不同入口下的首选网址。
  • 为不同的公开主机维护准确的站点地图，提交真实且可访问的规范页面。
  • 内部导航使用可点击的 HTML 链接，不要只依赖 JavaScript 事件跳转。
  • 搜索收录与网站分析是两回事：统计服务断开时不应把实际访问量写成零。

Google 和 Bing 都把站点地图视为帮助发现网址的线索，但并不承诺收录、排名或流量。正式效果需要结合 Webmaster Tools 的真实点击与曝光数据判断。

五、一次完整的上线验收应该保存什么

  1. 本次提交的 SHA、GitHub CI 链接与构建结果。
  2. 正式域名及备用域名的 HTTP 状态、标题和页面关键内容。
  3. 手机与桌面端的浏览器交互测试，特别是搜索、导航与横向滚动。
  4. 异常接口单独标注，不让非关键统计错误掩盖公开网页已发布的事实，也不将真正故障当成健康。
  5. 至少保留可恢复的历史版本，并把详细测试报告放在不公开的备份目录中。
