Windows 远程 SSH 连不上？按网络、端口、身份三层排查

不用先重装 VS Code，也不用直接关闭防火墙。先确认是哪一层断开，避免把 IP 变化、服务未启动和密钥认证失败混为一谈。

首次发布：2026 年 11 月 25 日 · 结合实际部署经验持续核验

一、先把连接链路分成三层

对 Windows 主机而言，远程连接通常同时涉及虚拟网络、TCP 端口和 SSH 身份验证。三层的错误提示不同，处理顺序也不同。VS Code Remote-SSH 只是 SSH 客户端入口；如果普通 SSH 尚未连通，重复卸载 VS Code 通常不能解决根因。

观察到的现象优先检查下一步
ZeroTier / Tailscale 显示离线双方客户端、服务状态及设备地址先恢复虚拟网络，不要操作远端 SSH 密钥
地址能 Ping，但 22 端口不通sshd 服务、监听地址、Windows 防火墙在目标主机本地或既有可信远程会话中诊断
22 端口可达，却出现 Permission denied用户名、私钥、公钥授权与 ACL核对正确 Windows 账户，不要随意覆盖 authorized_keys
REMOTE HOST IDENTIFICATION HAS CHANGED机器身份与主机密钥指纹通过独立可信渠道确认新指纹，不能盲目忽略校验
SSH 已连上，VS Code 无法打开远程窗口Remote-SSH 日志、服务器端扩展及权限仅在基础 SSH 验证成功后排查扩展

二、客户端先运行两条只读检查

将示例中的地址替换成你在 ZeroTier 或 Tailscale 中确认的目标设备地址；不要照抄示例 IP 当作真实主机。

Test-NetConnection 目标虚拟网络IP -Port 22
ssh -v 用户名@目标虚拟网络IP

TcpTestSucceeded : True 只证明 TCP 端口可建立连接，不等于已经有 SSH 管理权限。第二条命令会提供连接协商和认证相关日志；诊断时可以隐藏用户名、内部 IP 与密钥位置，不要上传私钥或密码。

三、目标 Windows 主机上的服务检查

当你已获准进入目标机器的本地终端或可信远程会话，可以执行下列只读命令：

Get-Service sshd
Get-NetTCPConnection -LocalPort 22 -State Listen
whoami
$env:USERPROFILE

特别注意：C:\Users\某目录 不一定等于实际登录账户名。配置公钥时要确认 SSH 使用的真实账户是否属于管理员组，管理员账户和普通账户的授权文件与 ACL 处理方式可能不同。

四、别把“连得上”变成新的安全问题

  • 优先使用已授权的 ZeroTier、Tailscale 或其他私有网络，不必为了 SSH 测试将 22 端口对公网开放。
  • 保留 SSH 主机指纹校验，确认机器身份后再接受新增主机密钥。
  • Windows 防火墙应保留；需要授权规则时尽量约束来源地址和网络接口。
  • 如果服务器正在进行科研计算或数据处理，先保证任务和文件安全，再考虑服务重启。
  • 将测试限制在获得授权的电脑；不要借用不明来源的自动修复脚本。

五、修复后这样验证 VS Code

  1. 普通终端先用相同地址、用户名和密钥连接成功。
  2. 在本机 SSH config 为目标主机设置简洁的 Host 别名和正确的 HostName。
  3. 在 VS Code 中选择 Remote-SSH: Connect to Host。
  4. 如连接失败，仅查看 Remote-SSH 输出面板中本次失败步骤，并与终端的 SSH 日志对照。

如果公网域名访问异常但私有网络仍连通，还要把 HTTP 站点、反向代理、Cloudflare Tunnel 与 SSH 四者分开检查；它们不是同一个服务。
